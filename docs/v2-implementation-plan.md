# V2 전환 설계 및 구현 계획

작성일: 2026-10-28

상태: [V2 요구사항](v2-requirements.md)에 대한 **후속 업무 기능 설계 제안**. 독립 인프라 배포·연결 검증은 완료했으며, 아래 고객 업무 모델·테이블·도구 후보는 현재 구현과 구분한다.

**후속 결정으로 배포 구조 변경:** V1과 같은 서버·DB에 추가하지 않는다. `v2/`의 별도 패키지·컨테이너, 새 Cloud Run 서비스·Neon 별도 프로젝트·독립 배포 브랜치를 사용한다. 현재 구현 범위와 실행 절차는 [V2 배포 가이드](v2-deployment.md) 참조. 아래 업무 모델과 S0~S5는 후속 기능 계획이며 전체 구현 완료를 뜻하지 않는다.

## 1. 기본 결정 제안

1. 계산 엔진을 유지하되 V2용 identity·권한·결과 어댑터를 분리한다. 금액 계산을 외부 AI로 옮기지 않는다.
2. 기존 `users`를 재해석하거나 V1 DB에 테이블을 추가하지 않는다. 별도 V2 DB와 독립 schema migration을 사용한다.
3. V1 `/mcp`·개인용 키는 유지하고 새 V2 URL의 `/mcp`·업무용 자격을 분리한다.
4. V2 업무 기능이 준비되기 전에는 인프라 도구만 제공한다. V1로 자동 fallback하거나 업무 서비스 준비 완료로 표시하지 않는다.
5. 운영 DB 접근·기존 사용자 연결·키 확대·배포는 이 문서 작업의 범위가 아니다.

## 2. 요청 처리 구조

```text
설계사 개인 AI 클라이언트
  └─ 새 V2 서버의 Streamable HTTP /mcp + 업무용 자격
      └─ actor/workspace/key scope 확정
          └─ 활성 membership 및 요청 제한 확인
              └─ client_access + processing_authority 확인
                  └─ 계약/특약/검증 근거 소유 관계 확인
                      └─ V2 업무 서비스·repository
                          └─ 확인된 보험·규칙 스냅샷
                              └─ 결정론적 계산 엔진
                                  └─ 버전·보류 사유를 포함한 구조화 결과
```

- 새 request identity에는 actor·workspace·key ID·허용 scope만 담는다. 고객은 매 호출 명시한다.
- 신원은 요청 범위에 한정하고 요청 종료·오류·취소 후 정리한다. 전역 가변 상태나 이전 요청의 고객 선택을 재사용하지 않는다.
- 인증 미들웨어뿐 아니라 업무 서비스와 DB 쿼리도 같은 권한 경계를 강제한다.
- 원격 업무 데이터에 직접 연결하는 무인증 stdio 모드는 제공하지 않는다. 초기 stdio는 분리된 합성 테스트 DB로 한정한다. 향후 로컬 프록시가 필요하면 원격 인증 경계를 그대로 사용한다.
- 장시간 연결에서도 매 도구 호출마다 키·소속·고객 권한의 유효성을 재검사한다. 철회 완료 후 시작된 호출은 거부하며, 진행 중 쓰기는 커밋 전에 다시 확인하는 경계를 정의하고 동시 철회 테스트를 둔다.

## 3. 논리 데이터 모델 — 테이블명은 후보

| 테이블 | 핵심 필드·제약 |
|---|---|
| `v2_actors` | 내부 ID, 비민감 표시명, 활성 상태 |
| `v2_workspaces` | 내부 ID, 개인/대리점 구분, 활성 상태 |
| `v2_memberships` | actor·workspace, 역할, 활성 상태; 조합 유일 |
| `v2_credentials` | membership, 키 해시, scope, 만료·폐기 시각; 해시 유일 |
| `v2_clients` | workspace, 불투명 client ID, 별명, 버전, 생성·보관 기한 |
| `v2_client_access` | workspace·client·membership, 읽기/쓰기/평가 권한, 철회 상태 |
| `v2_processing_authorities` | workspace·client, 목적·범위, 근거 참조, 유효·철회 시각, 기록자 |
| `v2_policies` | workspace·client, 계약 참조, 보험 데이터, 버전; 고객별 계약 참조 유일 |
| `v2_policy_riders` | workspace·client·policy 소속, 구조화 특약, 버전, 검증 조건 참조 |
| `v2_rule_revisions` | 규칙의 불변 버전, 적용 상품·기간, 출처 참조, 검토자·검증 상태 |
| `v2_audit_events` | 허용된 최소 메타데이터만, 별도 보관 기한 |
| `v2_idempotency_records` | workspace·actor·tool·키의 범위, 입력 HMAC, 대상 ID·처리 상태·만료 |

### 데이터 무결성

- 복합 FK/유일 제약으로 workspace-client-policy-rider와 membership의 소속 일치를 강제한다. SQLite에서도 FK 검사를 활성화한다.
- 모든 고객 쿼리는 인증된 workspace와 client 범위로 제한한다. ID의 추측 어려움은 권한 검사의 대체 수단이 아니다.
- 공유 규칙은 고객 정보 없는 카탈로그로 제한한다. 고객별 검증 근거는 다른 고객에게 참조시키지 않는다.
- 자료 처리 권한 등록 전 생성 가능한 고객 정보는 최소 별명·내부 ID뿐이다. 보험·특약을 넣는 등록 API로 우회하지 못하게 한다.
- 생성자에게 최초 고객 접근 권한을 부여하더라도 그 권한은 유효한 처리 근거를 대체하지 않는다.
- 개인용 `user_id`와 V2 고객 사이의 연결은 명시적 이행 매핑으로만 만든다. 별명·회사·상품명이 같다는 이유로 자동 연결하지 않는다.

## 4. 인증과 AI 클라이언트 연결

- 첫 구현은 별도 업무용 키와 운영자 CLI 발급을 제안한다. 같은 대리점도 설계사별 자격을 발급한다.
- 헤더 키를 지원하는 클라이언트에서만 이 연결을 지원한다고 명시한다. 기존 `X-User-Id`를 V2 고객 선택이나 역할 지정에 재사용하지 않는다.
- UI에서 URL만 입력할 수 있거나 OAuth 연결만 지원하는 AI는 별도 검증 대상이다. 정적 Bearer 키를 OAuth라고 표현하지 않는다.
- 대상 AI의 네이티브 원격 연결에 OAuth가 필수면 공식 MCP 인증 요구사항을 확인해 별도 구현 작업으로 추가한다. 키를 도구 인자·URL·채팅으로 우회 전달하지 않는다.
- 인증용 메타데이터/승인 경로가 필요해도 이는 인증 제어 경로이지 업무 REST·CRM 확장이 아니다. 별도 보안 검토를 거친다.
- 키 발급·소속 추가·타인 고객 권한 부여·검증 규칙 승인은 초기 일반 MCP 도구에 노출하지 않는다.

### 상호운용 기록 양식

| AI 앱·플랜·버전 | 원격 MCP | 자격 전달 | 도구/Resource 열거 | 고객 등록·평가 | 폐기/보류/오류 | 결과 |
|---|---|---|---|---|---|---|
| 첫 파일럿 대상: 미정 | 미시험 | 미시험 | 미시험 | 미시험 | 미시험 | 지원 미확정 |

지원 선언은 실제 클라이언트 시험으로만 한다. 로컬 SDK 테스트만으로 특정 상용 AI 앱의 지원을 보장하지 않는다.

## 5. 계산·응답 어댑터

- `domain/evaluator.py`는 기존 계산의 기준으로 삼되, V2 입력 정규화·검증과 출력 변환을 명시적으로 추가한다.
- 현재 진료비 기본값 0을 ‘판독 확인된 0원’과 구별할 V2 nullable 입력을 설계한다. 필수 금액이 미확인된 경우 엔진 호출 전 보류한다.
- 현재 엔진은 일부 미확인 출처·미매핑 항목을 별도 목록으로 반환하므로 V2 어댑터는 이를 담보별 보류 항목으로 정규화한다.
- `COMPLETE`는 평가 범위 내 모든 항목의 판정 가능을 뜻한다. 하나라도 보류되면 `PARTIAL`, 전부 보류/대상 없음이면 `NOT_EVALUATED`다. 담보별 `EXCLUDED`도 완결된 판정일 수 있지만 지급 승인은 아니다.
- 복수 실손 비례보상·누적 한도·기청구액 등 미지원 계산 조건을 식별하고, 미지원 범위는 단순 합산하지 않고 보류·제약으로 반환한다.
- 보험·특약·규칙을 일관된 스냅샷으로 읽고 버전을 응답한다. 재계산은 호출자가 진료 입력을 다시 제공한다. 서버가 진료 내역을 보관해 재현한다고 약속하지 않는다.
- 기존 `rule_config_override`를 그대로 신뢰하는 V2 경로를 만들지 않는다. 검토된 불변 조건 버전을 참조할 때만 검증 게이트를 통과시킨다.
- 승인된 조건을 기존 엔진에 전달하는 방식은 회귀 테스트로 확정한다. V1의 기존 결과나 미검증 데이터를 문서 작업에서 변경하지 않는다.

## 6. 재시도·동시성·감사

- 상태 변경 도구는 `idempotency_key`를 요구한다. 범위는 workspace·actor·tool이며 client/대상·입력을 요청 지문에 포함한다.
- 지문은 정규화 입력에 대한 서버 비밀 기반 HMAC으로 제안한다. 원문·단순 저엔트로피 입력 해시·전체 응답은 저장하지 않는다. 비밀 버전·TTL·순환 절차를 관리한다.
- 업무 변경과 멱등 레코드를 같은 트랜잭션으로 확정한다. 동시 요청의 키 유일 제약을 처리하고 같은 키/다른 입력은 충돌로 반환한다.
- 재호출도 인증·권한·처리 근거를 다시 검사한다. 완료된 쓰기는 대상 ID·적용 버전·행위 결과의 최소 확인만 반환하며, 과거 상세 본문을 재전송하지 않는다. 최신 상세는 별도 조회한다.
- 수정·삭제는 `expected_version` 조건부 갱신을 사용한다. 다른 쓰기가 먼저 완료됐으면 조용히 덮어쓰지 않는다.
- 평가는 상태 변경이 없으며 입력/결과 캐시나 멱등 본문 저장을 하지 않는다. 합성 입력으로 결정론적 재호출을 시험한다.
- 감사 기록 실패 정책: 보호된 조회·쓰기의 필수 감사 이벤트를 기록할 수 없으면 fail-closed한다. 쓰기와 감사는 같은 트랜잭션으로 확정한다. 운영 오류는 민감정보 없는 코드만 반환한다.
- 일반 로그·APM·HTTP 프록시·예외 추적 모두에서 인증 헤더·MCP 본문 캡처를 금지한다. 운영 키/고객 데이터 없이 합성 민감 표식으로 누출 여부를 시험한다.
- 호출 제한·만료 키·권한 철회는 Cloud Run 다중 인스턴스에서 일관되어야 한다. 프로세스 메모리의 카운터만으로 운영 제한을 구현하지 않는다.

## 7. 단계별 구현과 완료 기준

각 단계는 별도 `feat/<name>` 브랜치에서 구현하고 테스트한다. 아래는 아직 실행하지 않은 작업 계획이다.

| 단계 | 작업·주요 파일 후보 | 완료 기준 |
|---|---|---|
| S0 계약 고정 | V2 스키마·reason code·합성 fixture, 대상 AI 선정 | 실제 클라이언트 인증 방식 결정, 법률·보관 및 규칙 검토 담당 지정 |
| S1 신원·격리 | `db/tables.py`, V2 migration, `domain/security.py` 주변의 별도 V2 모듈, `api/auth.py` 라우팅 | actor/workspace/membership/자격 분리, V1 회귀·V2 무권한 격리 통과 |
| S2 고객·권한 | 별도 V2 repository/service 및 관리 CLI | 고객 등록·자료 처리 권한·담당 권한·철회, 쿼리/하위 ID 격리 통과 |
| S3 보험·검증 | V2 보험/특약 모델, 규칙 revision·검토 CLI | 복수 계약 식별, 미검증 override 우회 차단, 동시 수정·중복 요청 통과 |
| S4 MCP·평가 | 별도 V2 MCP 모듈, 결과 어댑터, 제한·감사 경로 | 제안 도구·스키마·상태·보류·비저장·분산 제한·삭제 수명 검증 |
| S5 파일럿 | `tests/`, 연결·운영·복구 가이드, 실제 대상 AI | 실제 원격 E2E, PostgreSQL·다중 인스턴스·이행 리허설 및 출시 게이트 통과 |

요구사항 R01~R11은 각 단계의 인수 테스트로 연결한다. R09·R11 및 법률/약관 검토는 단위 테스트 통과만으로 완료 처리하지 않는다.

## 8. 필수 시험 목록

| 범주 | 최소 시험 |
|---|---|
| 인증 | 누락·위조·만료·폐기 키, 비활성 소속, V1/V2 키 교차 사용, 지속 연결 중 철회 |
| 격리 | 다른 공간/같은 공간의 미배정 고객, client와 다른 policy/rider ID 조합, 목록·건수·커서·근거의 누출 |
| 권한 | 읽기 전용 쓰기 시도, 평가 scope 부재, 처리 근거 만료·철회, 소속 관리자의 무배정 고객 조회 |
| 수명 | 보관 기한 만료 시 차단, 권한 철회, 고객 삭제·하위 정리·백업 반영, 감사 최소 보존 |
| 계산 | 미입력과 0원, 미확인 진료 사실, 미검증 규칙, 증권 출처 진술만 있는 override, CUSTOM 보류, 복수 실손 |
| 계약 | 평가 없음/전부 보류/부분 계산/검증 제외, null과 0 구분, 식별자·규칙 버전, MCP 오류·도구 annotations |
| 동시성 | 같은 멱등 키 동시 등록, 같은 키의 다른 입력, 오래된 버전 수정, 권한 철회와 쓰기의 경합 |
| 상태 | 병렬 요청 identity 분리, 예외·취소 후 정리, 컨테이너 재시작·스케일링, 감사 저장 장애 |
| 누출 | DB·로그·캐시·APM·큐에 진료 입력/결과와 인증 비밀이 남지 않음, 에러 입력 반사 금지 |
| 이행 | 개인 데이터·키 보존, 모호한 매핑 거부, dry-run, 재실행, 부분 실패 복구 |
| 실제 AI | initialize·도구/Resource 열거·보험 등록·보완·평가·오류/철회 및 비밀 전달 방식 |

DB 관련 시험은 SQLite와 PostgreSQL 양쪽에서 수행한다. 계산 기준 fixture는 합성 자료 또는 별도 사용 허가·비식별 검토된 자료만 사용한다.

## 9. 기존 데이터 전환 및 복구

1. 새 V2 DB에만 버전 관리된 migration을 실행한다. V1 DB나 기존 시작 시 `create_all`/컬럼 추가 코드는 변경하지 않는다.
2. 스테이징 합성 DB에서 dry-run으로 대상·충돌·건수만 확인한다. 보고서에 고객명·보험 상세·비밀을 기록하지 않는다.
3. 기존 개인용 데이터는 기본적으로 그대로 둔다. 요청된 대상만 소유자·처리 권한·검증 상태를 확인해 명시적 매핑으로 이행한다.
4. 기존 `(user_id, company, product_name)` 기준에서 이미 합쳐진 계약은 자동 복원하지 않는다. 자료 확인 없이 계약을 분리·추정하지 않는다.
5. 이행된 출처·override는 자동 검증하거나 공유하지 않는다. 새 업무용 자격을 별도로 발급하고 개인용 키를 승격하지 않는다.
6. 재실행 가능한 이행 ID·건수·대상 매핑을 관리하고, 실패 시 기존 개인 경로는 유지한다. 운영 실행 전 백업·복원 및 롤포워드/중단 절차를 리허설한다.
7. 문제 시 신규 V2 호출·쓰기를 차단하고 수정한다. V2에 생성된 고객 데이터를 무조건 삭제하거나 V1에 역기록하지 않는다.

## 10. 이번 문서 작업과 다음 구현의 경계

- 인프라 후속 변경: `v2/`에 별도 실행 코드·의존성·migration·키·테스트·컨테이너·구축 스크립트, 독립 CI/배포 워크플로 추가. V1 실행 파일과 워크플로는 유지한다.
- 다음 기능 구현: 고객별 권한·처리 근거·자료 수명·감사·호출 제한 및 업무 도구. 현재 workspace context만으로 고객 처리 준비가 끝난 것은 아니다.
- 인프라 실제 검증: Cloud Run·Neon DB·WIF·배포 파이프라인·인증 MCP 연결 검증 완료. 버전·실행 결과는 STATUS 및 배포 가이드 참조.
- 미실행: V1 운영 DB 조회·이행, 실제 설계사 운영 키 발급, 상용 AI의 신규 호환성 검증과 고객 업무 도구 구현.
